# 50 — v3.1 Phase 2 Implementation Plan

> Concrete sequenced sub-tasks for the v3.1 windowed-homebrew Phase 2 work.
> Pre-requisite: `docs/49_v3.1_windowed_homebrew_design.md` design has been
> approved; v3.0.1 + the Phase-1 feasibility experiment have shipped (commit
> `35b5ce3b`, tag `v3.0.1-stable`).
>
> Each sub-task is sized to be commit-shippable on its own, gated, and
> reversible. Order is **dependency-aware** — earlier tasks unblock later
> ones; you don't have to do them in this exact order, but skipping a
> dependency means the later task can't HW-test.

---

## Sequencing principle

The v3.1 implementation has FIVE concrete sub-systems that must land:

1. **uLoader vi service type** — make hbloader's vi session capable of
   routing frames to an indirect layer instead of the direct scanout.
2. **uSystem new SMI command** — `LaunchHomebrewWindowedLibraryApplet`
   alongside the existing `LaunchHomebrewLibraryApplet`. Parallel API; the
   old full-screen path stays untouched.
3. **uSystem applet-mode branch** — call `appletCreateLibraryApplet` with
   `LibAppletMode_BackgroundIndirect` on the new SMI path. Acquire and
   surface the `IndirectLayerConsumerHandle`.
4. **uSystem concurrent-applet state machine** — the `la::IsActive()`
   serial gate must allow uMenu to remain alive while a windowed library
   applet runs. This is the biggest piece (~300–500 LOC).
5. **uMenu windowed-launch path** — new `OpenWindowedHomebrew(path, title)`
   method that calls the new SMI, opens a `QdWindow`, runs the capture
   loop, handles NRO exit.

Plus three engineering items that come up along the way:

6. **`viInitialize` Plutonium-coexistence experiment** — confirm whether
   raising the SDL2 vi session to `ViServiceType_Manager` works, or
   whether we need to tear-down + re-init.
7. **Chrome layer composition** — uMenu's window frame rendering moves
   from the default-display layer to a `vi:m` max-Z managed layer (Tesla
   technique).
8. **Input forwarding** — v3.1 MVP ships with NO controller input to the
   windowed NRO; the user uses the window via touch on the title bar/
   resize handle. Controller forwarding is v3.1.x.

## Task 1 — uLoader vi service type change (1 line; lowest risk)

**Goal:** uLoader currently calls (transitively, via libnx default) the
`vi:u` user service. To route frames into an indirect layer rather than
direct scanout, it must use `vi:s` (system) or `vi:m` (manager). Per BG-4's
audit, `vi:s` is sufficient and is the minimum-privilege change.

**Files:**
- `src/projects/uLoader/source/main.cpp` (or wherever `viInitialize` is
  called — find via `grep -n viInitialize src/projects/uLoader/source/`)

**Change:**
```c
// BEFORE
viInitialize(ViServiceType_Default);      // = vi:u
// AFTER
viInitialize(ViServiceType_System);       // = vi:s — required for indirect layer
```

**NPDM:** uLoader's NPDM `service_access` needs `vi:s`. Per the docs
archaeology (`docs/AUDIT-NPDM-uMenu-vi-access.md`), uLoader's current
service_access already includes vi-family service hosts; verify the
specific entry exists or add it.

**Exit criterion:**
- uLoader.nso rebuilt clean.
- Booting v3.0.1 + the new uLoader binary launches an NRO normally
  (no regression to the existing full-screen launch path; we haven't
  changed launch MODE yet, just service TYPE).

**Risk:** Low. The change is a no-op for the existing full-screen path
because `vi:s` is a superset of `vi:u`. The only failure mode is if
uLoader's NPDM lacks `vi:s` — fixed by adding the entry.

**Commit shape:** Single commit, message
`uLoader: vi service type Default → System for v3.1 indirect-layer prep`.

## Task 3 — uSystem applet-mode branch (BackgroundIndirect)

> **STATUS 2026-05-19: TERMINATED — BLOCKED BY HOS PRIVILEGE GATE.**
>
> All four slices (1–4) landed and HW-tested.  The launch chain WORKS:
> uMenu can spawn a BG-indirect library applet via
> `appletCreateLibraryAppletSelf` and obtain a non-zero
> IndirectLayerConsumerHandle.  The actual frame fetch via
> `viGetIndirectLayerImageMap` is BLOCKED — returns 2114-0011 (vi module,
> description 11, undocumented Nintendo error) regardless of:
>   • vi service tier (vi:u, vi:s, vi:m all denied)
>   • Retry timing (10 retries × 100ms all return identical rc)
>   • Required-memory-info query at same handle (which DOES succeed)
>
> Strong evidence the gate is on AppletType — `viGetIndirectLayerImageMap`
> is Nintendo's qlaunch-private primitive for the home-menu album view,
> and stock HOS gates it behind AppletType_SystemApplet or similar.
> uMenu is `AppletType_LibraryApplet` from AM's perspective (loaded via
> ECS under the qlaunch slot, declared LibraryApplet to libnx).
>
> Without Atmosphère vi-mitm patches OR a fundamental change to how uMenu
> is launched (which risks breaking finalize handling, applet messaging,
> and the existing foreground launch path), `viGetIndirectLayerImageMap`
> is unreachable from uMenu.
>
> **v3.1 pivoted to the Tesla overlay model** — see new section
> "v3.1 architecture pivot" below.

## v3.1 architecture pivot: Tesla overlay model

> **Status as of 2026-05-19: PROPOSED.**

The IndirectLayer capture approach is dead.  v3.1 pivots to a different
model based on the Tesla overlay technique (Ultrahand, OverlayLoader,
etc.):

### Concept

The homebrew NRO launches **fullscreen via the existing foreground
LaunchHomebrewLibraryApplet path** — no concurrent-applet state-machine
work needed.  uSystem (the persistent qlaunch process) owns a **vi:m
max-Z managed layer** that renders window chrome on top of whatever
applet is currently in the foreground.

The chrome layer:
- Adds the layer to all 8 ViLayerStacks (Default, Application,
  ApplicationForDebug, etc.) via IManagerDisplayService cmd 6000.
- Renders a thin border + title bar at the top of the screen.
- Title bar shows "Q OS — \[NRO filename\]" plus action buttons
  (close X, minimize-back-to-uMenu).
- Touch on close X → uSystem terminates the active LA and re-launches
  uMenu.
- Touch on minimize button → same effect (no real "minimize" since HOS
  can't suspend LAs).

### Architecture

```
                ┌─────────────────────┐
                │     vi:m overlay    │ ← uSystem owns, max-Z, all stacks
                │  [Q OS — sphaira]X  │
                └─────────────────────┘
                ┌─────────────────────┐
                │                     │
                │   sphaira running   │ ← foreground LA (uLoader-applet)
                │     fullscreen      │
                │                     │
                └─────────────────────┘
```

### Why uSystem owns the overlay

uSystem is the qlaunch process — it stays alive across applet
transitions.  uMenu can't own the overlay because uMenu finalizes when
it hands off to the next LA.  A new sysmodule could own it but that's
a bigger lift; uSystem already has all the IPC + lifecycle hooks we'd
need to extend.

### Rendering challenge

uSystem doesn't have a renderer (no SDL2).  Initial rendering options:

1. **vi:m fatal primitives**: `viManagerDrawFatalRectangle` +
   `viManagerDrawFatalText32`.  Limited but enough for basic chrome
   (border, title bar text, button outlines).
2. **Software rasterizer + nvDrv framebuffer**: ~1000 LOC to roll a
   minimal one.  More flexibility (color buttons, anti-aliased borders).
3. **Port a chunk of Tesla GUI**: Borrow Ultrahand's rendering lib.
   License-compatible, but adds a third-party dependency.

MVP: option 1 (vi:m fatal primitives) — proves the architecture works
with minimal new code.  Iterate to option 2 if visual quality
demands it.

### Input

uSystem's MainLoop already calls `hidScanInput()` for HOME-button
handling.  Extend the same scan to read touch coordinates and dispatch
to the close X / minimize-back hit boxes.

### Sequencing for v3.1 Tesla overlay

| Slice | What | Effort |
|---|---|---|
| **T1** | uSystem creates vi:m max-Z managed layer, adds to all 8 stacks, renders one colored test rectangle in a known position.  HW-verify the rect is visible on top of uMenu desktop and on top of a running LA. | 1–2 days |
| **T2** | Replace test rect with chrome: thin border + title bar with NRO name. | 2 days |
| **T3** | Touch input: detect tap on close-X hit box, terminate active LA, re-launch uMenu. | 1 day |
| **T4** | Settings entry: toggle "Show window chrome on homebrew launches" (default off until stable). | 1 day |
| **T5** | Polish: title bar uses theme colors, smooth transitions when overlay shows/hides, multi-NRO chrome stacking if applicable. | 2 days |

**Total v3.1 Tesla MVP**: ~7–10 days focused work.

### What this is NOT

- Not "windowed homebrew" in the literal sense — NRO is still fullscreen.
- Not "multi-window" — only one NRO at a time, chrome is a decoration.
- Not "minimize" in the suspend sense — minimize just closes the NRO
  and reopens uMenu (HOS can't suspend LAs without crash-recovery
  hooks).
- Not GPU-rendered — uSystem uses simple software primitives.

### What this IS

- Window-frame UX for the user — they see chrome around running NROs.
- Single-tap close from any homebrew (no need to navigate the NRO's
  internal exit flow).
- Foundation for future real windowing once Atmosphère vi-mitm or
  a sysmodule renderer ships.

## Task 4 — uSystem concurrent-applet state machine (~300–500 LOC)

**Goal:** Today's `la::IsActive()` gate (`main.cpp:1150` per BG-2) blocks
the next applet launch until the current one finishes. v3.1 needs both
uMenu and the windowed library applet alive simultaneously.

**Files:**
- `src/projects/uSystem/source/main.cpp` lines around 1100–1200 (the
  `la::*` state machine).
- New: `src/projects/uSystem/source/applet_state.cpp` for the concurrent
  tracking.

**Design:**
- Today: single global `la::Active` flag + `IsActive()` check.
- New: track applets by **launch mode**:
  - `AllForeground` → still serial (one at a time, blocks parent).
  - `BackgroundIndirect` → parallel; parent stays alive; multiple
    BackgroundIndirect applets MAY be allowed (BG-2 said the state machine
    is currently sequential; making it concurrent requires actually
    rewriting the gate).
- For v3.1 MVP: allow ONE BackgroundIndirect applet at a time + uMenu.
  Multi-windowed-NRO ships in v3.1.x or v3.2.

**Exit criterion:**
- uMenu launches an NRO via the new SMI path, NRO renders to the indirect
  layer, uMenu stays alive and visible.
- Closing uMenu's window via the × button triggers NRO clean exit.
- Re-launching the same NRO afterward works.

**Risk:** High. This is the architectural change. State-machine bugs here
will surface as race conditions, leaked applets, or boot-loop hangs.
**Recommendation:** before this task, write a minimal-reproducer test
that toggles uMenu↔windowed-NRO↔uMenu 50 times in a row to surface state
leaks early.

**Commit shape:** Multiple commits, e.g.:
- `uSystem: introduce AppletState struct for per-applet tracking`
- `uSystem: refactor la::Active to support BackgroundIndirect concurrent`
- `uSystem: NRO-exit cleanup path for BackgroundIndirect applets`

## Task 7 — Chrome layer composition (Tesla technique)

**Goal:** Per design doc §2.3, uMenu's window frame renders on a `vi:m`
max-Z layer added to all 8 `ViLayerStack_*` variants. This is what
Tesla overlays do (Ultrahand, OverlayLoader, etc.).

**Pre-requisite:** Task 6 answer.

**Files:**
- New: `src/projects/uMenu/source/ul/menu/qdesktop/qd_ChromeLayer.cpp`.
- Modifies how `QdWindow::OnRender` flushes — output goes to the chrome
  layer's surface instead of the default-display surface.

**Behavior:**
- `viCreateManagedLayer` to create a layer in the manager session.
- `viSetLayerZ(viGetZOrderCountMax())` to push to top.
- `IManagerDisplayService cmd 6000` to add the layer to all 8 stacks.
- Render uMenu chrome (windows, dock, hot-corners) into this layer.

**Exit criterion:** chrome paints over the captured NRO content correctly;
no z-fight; no visible seam.

**Risk:** Medium. Tesla overlays work in production so the technique is
proven, but the exact integration with Plutonium's render path is
uncharted.

**Note:** A simpler MVP path is to render the chrome via SDL into the
SAME layer where uMenu already renders (the default-display layer), with
the captured NRO content composited INSIDE the chrome's content viewport
— no separate vi:m layer. This is uglier (uMenu would be either fully
on top or fully behind the NRO, no per-window z-order), but it sidesteps
the Task 6 / Task 7 vi-session question entirely.

**Recommendation:** ship MVP with the simpler SDL-only path; queue the
Tesla vi:m chrome layer to v3.1.x once HW-stable.

## Task 8 — Input forwarding (v3.1.x — DEFER)

Per BG-2, NRO's `hidScanInput()` returns zeros in BackgroundIndirect mode.
Tesla overlays solve this via a button-combo intercept pattern.

**v3.1 MVP behavior:** windowed NRO receives NO controller input. User
interacts with the window via touch (title bar drag, resize handle, close
button) but the NRO inside is read-only — useful for things like sphaira's
catalog browse, JKSV's save view, etc., where you don't need controller
input from the windowed view.

**v3.1.x scope:** focus-gated input forwarding. When the NRO window is
focused: write HID state into a shared memory region the NRO can read
(needs an HBABI extension OR a libnx patch on the NRO side OR an Atmosphère
hid-mitm). All three options are non-trivial.

**Defer to a separate v3.1.x design doc.** Not in v3.1 MVP scope.
