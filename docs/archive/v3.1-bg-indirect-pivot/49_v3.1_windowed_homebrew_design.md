## 0. TL;DR

**v3.1 makes every NRO render full-screen at 1920×1080 into the applet slot it
already runs in today, while uMenu stays alive in the background, captures
the applet's framebuffer, and composites the captured pixels into a Q OS
window of any user-chosen size.**

- The NRO is **not modified**. There is no opt-in SDK, no HBABI extension, no
  per-NRO patch. The NRO thinks it's running full-screen as it always did.
- Q OS captures the applet's rendered output via the existing
  `vi:s CaptureScreenshot` mechanism (the same primitive the Album applet
  uses for screenshots).
- uMenu must change applet mode from the current `LibAppletMode_AllForeground`
  (which requires uMenu to die before hbloader can start) to
  `LibAppletMode_BackgroundIndirect`.  This is the only mandatory uSystem-
  side change.  **Important:** `LibAppletMode_Background` (mode 1) is
  compute-only with no display — wrong primitive.  `BackgroundIndirect`
  (mode 3) is the one that issues the `IndirectLayerConsumerHandle` we
  need for live frame capture.
- The HBmenu absorption in v3.0 freed memory + simplified the launch path,
  which is the structural foundation v3.1 builds on.
- The first feasibility question (which determines whether the design is
  buildable at all on Atmosphère/HOS 20.0.0): **does uMenu's NPDM grant
  `vi:s` service-access?** Pre-existing audit doc
  `docs/AUDIT-NPDM-uMenu-vi-access.md` will answer this; if no, we add the
  capability and rebuild — a known-tractable NPDM edit.

## 1. What the v3.0 README / ROADMAP got wrong about v3.1

The v3.0 cycle shipped public docs that contained four assumptions that
turned out to be wrong. They're listed here so future agents working from
this doc know what to ignore:

1. **"Sphaira already has windowed-mode hooks in its upstream, which makes
   it the lowest-risk first target."** — false. Sphaira has no such hooks.
   Source: `docs/49_v3.1_research_sphaira.md` (BG agent searched the full
   sphaira source; the words "windowed", "compositor", "embed", "hosted",
   "OOP" appear nowhere). Q OS extrapolation that I (the docs author) made
   when writing the v3.0 README; the creator never claimed this.

2. **"Redirect hbloader's nv-gfx output to a deko3d shared texture
   instead of letting it own the front buffer (requires Atmosphère mitm
   extension or a custom hbloader fork)."** — `vi:u` service mitm is
   structurally blocked. Source: `docs/49_v3.1_research_atmosphere_mitm.md`
   — the frame data flows through `IHOSBinderDriverRelay` which is a
   sub-session, never visible to SM mitm. Atmosphère mitm of `vi:u` gives
   zero access to frame content. This path is dead.

3. **"deko3d does support cross-process texture import."** — false. The
   deko3d public API does not. The underlying `nvmap` layer does via
   `NVMAP_IOC_EXPORT_FOR_ARUID`, but that's the "cooperative NRO opt-in"
   path which the creator explicitly rejected (see §2).

4. **"NROs would have to opt-in to a hosted protocol."** — also rejected by
   the creator. The v3.1 design must not require any NRO modification. The
   universal capture model in §2 replaces this.

Two assumptions that were correct and survive:

- **uMenu currently has to die before hbloader can launch.** True.
  `qd_DesktopIcons.cpp:4985-4998` calls `Finalize()` after
  `smi::LaunchHomebrewLibraryApplet` because the launch mode is
  `LibAppletMode_AllForeground`. v3.1 must change this.
- **The Photo Capture applet slot owns the NRO's framebuffer.** True. The
  NRO's libnx initializes its own vi connection inside that slot. We
  capture FROM the slot externally rather than redirecting INSIDE it.

## 2. The universal VM-in-window design (creator-corrected)

The model in one sentence: **the applet slot is a "VM"; uMenu is the host
window manager; the captured framebuffer is the VM's display, painted into
a window of whatever size on the Q OS desktop.**

### 2.1 Frame capture — UPDATED per BG-2 (2026-05-18 evening)

BG-2's deep dive into Atmosphère identified the correct production
primitive. The PRODUCTION mechanism is:

**`viGetIndirectLayerImageMap`** — `IApplicationDisplayService` cmd 2450
(documented in libnx `vi.h` line confirmed). This is the LIVE-FRAME path
that AM uses internally to composite library-applet output, not a
screenshot path. Properties per BG-2's audit:

- **Live frame**, not a snapshot — pixels are the current applet output
  rather than a captured-at-time-X buffer.
- Callable from `vi:u` service level — **no `vi:s` privilege escalation
  required**. uMenu's wildcard NPDM already grants this.
- Returns raw pixels (no JPEG decode pipeline). Layout: the buffer +
  stride + width/height come back together; the caller `SDL_UpdateTexture`s
  directly.
- Requires an `IndirectLayerConsumerHandle`. This handle is issued by AM
  ONLY when the library applet is launched in
  `LibAppletMode_BackgroundIndirect` mode. **The applet mode is the
  architectural pivot** — see §2.2.

The `capsscCaptureJpegScreenShot` primitive used in uSystem's USB-viewer
feature today is a SCREENSHOT path (heavier pipeline, JPEG-encoded
output, higher latency).

**Phase 1 experiment HW result (2026-05-18, v3.0.1 boot, HOS 20.0.0):**
`capsscInitialize` succeeds (rc=0x00000000, 0.52 ms — confirms uMenu's
NPDM grants caps:sc), but every subsequent `capsscCaptureJpegScreenShot`
call returns `rc=0x0000E0CE size=0` regardless of which `ViLayerStack`
target (Default / ApplicationForDebug / Screenshot / LastFrame).
Result-code decode: module 206 (capsrv), description 112 — undocumented
in libstratosphere's `capsrv_results.hpp` (gap between AlbumError
2–99 and ControlError 800–899).  Most plausible interpretation: capsrv
refuses to capture system-menu / library-applet output; the service
is meant for user-initiated screenshot during gameplay, not for parent
applets peeking at child renderings.

**Implication:** capssc is NOT a viable fallback for v3.1.  The production
path (`viGetIndirectLayerImageMap` + `LibAppletMode_BackgroundIndirect`)
is the ONLY path.  This is hardware-confirmed; no further fallback
research needed.  Phase 2 must work or v3.1 ships without windowed NROs.

- **Latency budget:** lower than the earlier 33 ms estimate because no
  JPEG encode/decode. BG-2 cites no specific number; real-hardware
  measurement still required.
- **Format:** raw `RGBA8` or `BGRA8` straight into a callable-provided
  buffer.
- **Frame rate:** real-hardware measurement required (Phase 2 deliverable).

### 2.2 uMenu must stay alive: `LibAppletMode_BackgroundIndirect`

The current launch path (per `docs/49_v3.1_research_hbloader.md` §4):

```
uMenu: smi::LaunchHomebrewLibraryApplet(path, "")
uMenu: FadeOutToNonLibraryApplet()
uMenu: Finalize()    ← uMenu PROCESS EXITS HERE
uSystem: !la::IsActive() guard fires
uSystem: ecs::RegisterLaunchAsApplet(/ulaunch/bin/uLoader/applet)
uSystem: appletCreateLibraryApplet(AppletId_Album, AllForeground)
uSystem: appletHolderStart(holder)
```

The block at `qd_DesktopIcons.cpp:4985-4998` enforces this — if we don't
call `Finalize()`, uMenu re-asserts foreground and silently kills hbloader
before the NRO can display (the v1.10.x cycle C1 fix that's been carried
forward since).

For v3.1 the new path is:

```
uMenu: smi::LaunchHomebrewLibraryApplet(path, BACKGROUND_INDIRECT)
uSystem: ecs::RegisterLaunchAsApplet(/ulaunch/bin/uLoader/applet)
uSystem: appletCreateLibraryApplet(AppletId_Album, LibAppletMode_BackgroundIndirect)
uSystem: appletHolderStart(holder)
uSystem: appletHolderGetIndirectLayerConsumerHandle(&handle)  ← bridge primitive
uSystem: hands handle back to uMenu via SMI response (or shared global)
uMenu: stays alive; opens a new QdWindow; runs the capture loop calling
       viGetIndirectLayerImageMap(buf, size, w, h, handle, &out_size, &out_stride)
       in a render-callback at the window's paint rate
```

`LibAppletMode_BackgroundIndirect` (mode 3) is the libnx primitive that
issues the `IndirectLayerConsumerHandle` we need.  Distinct from
`LibAppletMode_Background` (mode 1) which is compute-only with no
display — wrong primitive, would render black frames silently.  BG-2 +
BG-4 independently confirmed BackgroundIndirect is the mode we need.

### 2.3 Compositing in uMenu — TWO LAYERS, both confirmed by research

BG-6's Tesla audit closed a gap I hadn't fully thought through: how does
uMenu draw the window chrome (title bar, close button, drop shadow) ON
TOP of the captured NRO content? The answer is **Tesla's exact technique,
rotated 90° onto our use case**:

| Layer | Technique | Primitive |
|---|---|---|
| **NRO content (inside the window)** | live capture | `viGetIndirectLayerImageMap` + `BackgroundIndirect`-issued handle |
| **Window chrome (frame, buttons, label)** | overlay layer | `vi:m` managed layer at `viGetZOrderCountMax()`, added to all 8 `ViLayerStack_*` variants via `IManagerDisplayService cmd 6000` |

The chrome layer is **exactly what every Tesla overlay** already uses to
draw on top of any running applet/game. It's a proven, in-production
pattern. Q OS uMenu calls `viInitialize(ViServiceType_Manager)`,
`viCreateManagedLayer`, `viSetLayerZ` to the max, and the chrome paints
over everything — including the captured NRO content sitting in its
indirect layer below.

The Q OS window-manager primitive `QdWindow` already exists (v3.0 ships
with the windowing finalized). The NRO window is just another
`QdWindow` whose:

- **Content** is a single SDL texture updated each frame from
  `viGetIndirectLayerImageMap`.
- **Chrome** is the existing v3.0 frame rendering, but the rendering
  surface is the new `vi:m` managed top-Z layer rather than uMenu's
  default-display layer.

```
                            ┌──────────────────────────────────────────┐
                            │  uMenu (stays alive)                     │
                            │                                          │
                            │   QdWindow [NRO content]                 │
                            │   ┌────────────────────┐                 │
                            │   │ titlebar  × □ – ↗  │ ←  v3.0 chrome  │
                            │   ├────────────────────┤                 │
                            │   │                    │                 │
                            │   │ captured FB texture│ ←  v3.1 content │
                            │   │ (scaled to win_w/h)│                 │
                            │   │                    │                 │
                            │   ├────────────────────┤                 │
                            │   │ bottom-bar hint    │                 │
                            │   └────────────────────┘                 │
                            │           ↑                              │
                            │           │ vi:s CaptureScreenshot       │
                            └───────────┼──────────────────────────────┘
                                        │
                                        │ (cross-applet capture)
                                        │
                            ┌───────────┼──────────────────────────────┐
                            │  hbloader applet slot (Photo Capture)    │
                            │                                          │
                            │  NRO (sphaira / JKSV / RetroArch / etc.) │
                            │  draws full-screen 1920×1080 as today    │
                            │  (NRO is unmodified)                     │
                            └──────────────────────────────────────────┘
```

The window's `OnRender` callback runs the capture inline (or polls a
ring buffer filled by a capture thread, depending on what the
feasibility experiment in §6 reveals about latency under hardware).

### 2.4 What does NOT change

- The NRO. Zero modification.
- hbloader / uLoader. Possibly zero modification — see §4 risk.
- HBABI. No new `ConfigEntry` kinds.
- Atmosphère. No new sysmodule.
- Hekate. No bootloader changes.

What DOES change:

- uSystem's `smi::LaunchHomebrewLibraryApplet` IPC takes a new
  optional argument for applet mode (or a separate cmd).
- uSystem calls `appletCreateLibraryApplet` with `Background` instead
  of `AllForeground` when the windowed-mode flag is set.
- uMenu does NOT call `Finalize()` on the windowed launch path.
- uMenu opens a new `QdWindow` and starts the capture loop.
- uMenu's NPDM gains `vi:s` service-access permission if it doesn't
  already have it.

## 3. Input routing

The "window has focus → NRO gets input" semantics work like this:

- Q OS windows already have a focus model (v3.0 ships with focused-window
  tracking in `QdWindowManager`).
- When the NRO window is focused, uMenu forwards HID events through
  `hidProcess*` calls that the NRO can read normally (it has no idea the
  events came from a host window manager — the applet is the
  hid-foreground from its perspective).
- When the NRO window LOSES focus (user clicks another window, taps the
  dock, etc.), uMenu either:
  - **A.** Pauses HID forwarding (NRO sees no input, may pause itself).
  - **B.** Continues forwarding but routes hot-corner / window-control
    inputs to uMenu first (the user can move/resize the window without
    closing the NRO).

Option B is the better UX; Option A is the simpler implementation. v3.1
ships with Option A as the MVP, Option B comes in v3.1.x.

The complication: HID is owned by the foreground applet. In Background
mode, the applet may not have HID access by default. BG-2 audits the
exact HID-routing semantics under `LibAppletMode_BackgroundIndirect`. If the
windowed applet doesn't see HID at all in Background mode, we need
either:

- Atmosphère permission to virtual-input from uMenu's process
- Or a tiny relay sysmodule that re-injects HID into the applet

Both options expand scope significantly. The feasibility experiment in
§6 must measure HID behavior in Background mode before we commit to a
specific routing strategy.

## 4. Implementation phases

### Phase 1 — Feasibility experiment (1 evening)

**Goal:** prove `vi:s CaptureScreenshot` actually works from uMenu in
the current Atmosphère + HOS 20.0.0 environment.

**Deliverable:** a small patch in uMenu that, when a debug toggle is
flipped (from the top-right hot-corner Dev section), calls
`vi:s CaptureScreenshot` once per second against uMenu's own output and
logs:
- Return code
- Buffer size received
- First 16 bytes of pixel data (sanity check that we got real pixels)
- Total round-trip latency in ms

If the call returns clean pixels: Phase 2 starts. If it returns
permission-denied: NPDM needs editing (Phase 0.5, ~30 min). If it
returns "not supported in this configuration": we have a real problem
and need to consult BG-2's audit for alternative capture mechanisms.

**Exit criterion:** real-hardware log line proving capture works.

### Phase 2 — uSystem + uMenu pipeline (2–3 weeks)

**Goal:** end-to-end windowed-launch path working with one NRO.

**Sub-tasks:**
1. Extend `smi::LaunchHomebrewLibraryApplet` IPC to accept an `applet_mode`
   parameter (default `AllForeground` for back-compat; `Background` for
   windowed).
2. uSystem-side: branch on `applet_mode` when calling
   `appletCreateLibraryApplet`. Update the `ecs::RegisterLaunchAsApplet`
   call if the Background mode requires a different exefs redirect target
   (BG-4 audit will confirm).
3. uMenu-side: replace the `Finalize()` call in `LaunchIcon` with a new
   `OpenWindowedHomebrew(nro_path, title)` method that:
   - Pushes the `TargetInput` storage as today
   - Calls SMI with `Background` mode
   - Opens a fresh `QdWindow` titled with the NRO name
   - Installs a capture loop tied to the window's render callback
4. Capture loop: `vi:s CaptureScreenshot` → JPEG decode or raw blit →
   update window's content texture → invalidate window.
5. NRO-exit detection: when the applet holder's `StateChangedEvent`
   fires (signaling the NRO exited), close the window cleanly and free
   the capture resources.

**Exit criterion:** sphaira (or any unmodified community NRO) launched
from the desktop opens in a Q OS window I can move, resize, and close,
with sphaira running normally inside it at ≥20 fps.

### Phase 3 — Input + lifecycle polish (1–2 weeks)

**Goal:** make the windowed NRO feel like a real window.

**Sub-tasks:**
1. HID forwarding gated by window focus (per §3).
2. Multiple windowed NROs concurrently (if the applet model permits;
   BG-2 audit will say).
3. Window-coordinate input translation if BG agents surface a clean path.
4. Documentation: "your NRO already works in a Q OS window — here's
   how to launch it" user-facing doc, no developer doc needed since
   it's universal.

**Exit criterion:** two NROs windowed simultaneously, each in its own
window, each receiving input only when focused.

## 4.5 NRO compatibility matrix (BG-1 verdict)

BG-1 audited 17 community NROs. Headline: **11 of 17 will work cleanly**
with VM-in-window today; the rest need either NRO-specific awareness or
acceptance of minor compromises.

### Will "just work"

| NRO | FB model | Notes |
|---|---|---|
| **ftpd** | deko3d | Cleanest architecture; benign focus hook; dynamic 720p/1080p |
| **NX-Shell** | OpenGL/EGL | Fixed 720p, no focus hooks |
| **JKSV** | SDL2 | Fixed 720p, only an innocuous applet-type warning popup |
| sphaira | deko3d | Standard `nwindowGetDefault()` swapchain |
| Goldleaf | SDL2 | Plutonium-based (same UI lib as uMenu) |
| Tinwoo | deko3d | Standard |
| NXThemesInstaller | SDL2 | Standard |
| AIO Switch Updater | SDL2 | Standard |
| breeze | deko3d | Cleanly capturable (see hazard below for `LibraryApplet` self-declaration) |
| ftpd | deko3d | (duplicate — listed above as cleanest) |
| linkalho | SDL2 | Standard |

(Catalog-wide: 11 of 17 use `nwindowGetDefault()` via deko3d / OpenGL /
SDL2 — all read by `viGetIndirectLayerImageMap` without further effort.)

### Hazards to handle

| NRO | Hazard | Mitigation |
|---|---|---|
| **EdiZon SE** | Launches its own foreground `LibraryApplet` for account-select; will try to seize vi foreground | v3.1 documents "EdiZon SE not yet supported" — work around in v3.1.x |
| **RetroArch** | Polls `appletGetFocusState` every frame and pauses emulation when unfocused | Q OS keeps the applet slot foregrounded from RetroArch's perspective even when its Q OS window isn't focused; works but fragile across RetroArch updates |
| **breeze** | Self-declares `AppletType_LibraryApplet`; may affect `vi:s` layer targeting | Test on hardware; likely OK because we're using indirect-layer-image-map (vi:u-callable) not vi:s capture |
| **EdiZon SE** | Uses legacy `hidKeysDown` (pre-libnx2 API) | Input forwarding (when implemented in v3.1.x) needs to support both legacy + modern HID APIs |
| **Ultrahand** | Not a windowing target — it's a `.ovl` overlay loaded by `nx-ovlloader` | Treated as a v3.2+ catalog item (see §10), not v3.1 |
| **DBI** | Closed source | Unknown; HW-test only |

The pattern across all hazards: **modern (deko3d / OpenGL / SDL2) NROs
without focus-state-paranoia and without self-declared LibraryApplet
behavior** are the universal v3.1 happy path.

## 5. What is explicitly DEFERRED past v3.1

- **Nintendo applets (Album, Mii, Controllers, Web Browser).** Still
  firmware-rendered sysmodule processes. They DO respond to
  `vi:s CaptureScreenshot` in theory (the Album applet captures *itself*
  for screenshots), but the launch path goes through different SMI calls
  that may not accept `Background` mode. Park to "v3.2 maybe, v4 if
  Atmosphère adds something" until BG-2 has hard evidence either way.
- **Game (NCA) titles.** Retail and homebrew applications launched via
  `nsLaunchApplication` are different from library applets — they own
  the foreground exclusively. Windowing a retail game is out of scope.
- **Performance optimization.** v3.1 ships at whatever fps the
  feasibility experiment establishes. Speeding it up (e.g., a
  shared-memory variant via nvmap to avoid the JPEG decode cost) is
  v3.1.x or v3.2.

## 6. Feasibility experiment specification (lands in this session)

The experiment is the smallest possible code that answers the question
"does `vi:s CaptureScreenshot` return pixels from uMenu's NPDM today?"

### 6.1 The patch

A new file `src/projects/uMenu/source/ul/menu/qdesktop/qd_FrameCaptureExperiment.cpp`
containing:

```cpp
// Phase-1 feasibility experiment for v3.1.  Wired into the top-right
// hot-corner Dev dropdown as a new row "Frame capture test".  Tapping it
// invokes vi:s CaptureScreenshot once and logs the result.  No window,
// no compositing, no loop — just a single call + a log line that proves
// (or disproves) whether the primitive is available with uMenu's current
// NPDM service-access bits.

namespace ul::menu::qdesktop {
    void RunFrameCaptureExperiment();
}
```

The function:
1. Calls `viInitialize(ViServiceType_System)` (the `vi:s` privileged
   variant — `ViServiceType_Default` gets `vi:u` which doesn't have
   `CaptureScreenshot`).
2. Calls `viCaptureJpegScreenShot` (or whatever the BG-2 audit pins
   down) with a 1 MB buffer.
3. Logs: rc, returned size, first 16 bytes hex, total elapsed µs.
4. Calls `viExit()`.
5. Returns. Single-shot.

### 6.2 Wiring

Add one new row to the top-right hot-corner Dev section in
`qd_HotCornerRightDropdown.cpp`. Label: `"Frame capture test"`.
When tapped, calls `RunFrameCaptureExperiment()`. No further UI.

### 6.3 Build + deploy

`make umenu` from `src/`. Deploy uMenu binary to SD via the existing
flow. Boot. Tap the experiment row. Read the log.

### 6.4 What we measure

| Field | Source | Meaning |
|---|---|---|
| rc | viCaptureJpegScreenShot return | `0x00000000` = pixels returned; anything else = failure to investigate |
| size | output param | actual bytes written; expect ≥ a few KB for a real JPEG |
| first 16 bytes | log | `FF D8 FF ...` = valid JPEG header; `00 00 00 ...` = empty / black |
| elapsed µs | timing | actual latency on real hardware (vs the speculated 33 ms) |

### 6.5 Decision tree

- **rc = 0 + valid JPEG header → Phase 2 starts.** Universal-VM-in-window
  is feasible.
- **rc = permission-denied → NPDM patch (Phase 0.5).** Add `vi:s` to the
  service-access list, rebuild, retry. BG-5 docs audit confirms whether
  this is already present.
- **rc = "this applet can't be captured" → consult BG-2.** May need to
  capture a different applet target, or switch to a different primitive
  (e.g., `nv` mitm if it turns out to be possible after all).
- **rc = something else → log, regroup.** The experiment's purpose is to
  surface unknown unknowns; we expect at least one of these.

## 8. Risks + open questions

(Re-folded against BG findings before v3.1 implementation starts.)

1. **`LibAppletMode_BackgroundIndirect` does NOT give HID to the applet.**
   Confirmed by BG-2.  NRO's `hidScanInput()` returns zeros because HID
   focus stays with the parent.  See §3 — adds significant scope.  Tesla's
   button-combo intercept pattern (BG-6) is the candidate transferable
   technique for v3.1.x.
6. **Two `viInitialize` calls in one process — libnx service-guard risk.**
   Plutonium / SDL2 ALREADY hold a vi session inside uMenu (it's how the
   desktop renders).  The §2.3 design has uMenu making a SECOND
   `viInitialize(ViServiceType_Manager)` call to create the chrome
   max-Z layer.  libnx's `g_viServiceType` global guards against this
   and may silently fail the second init.  The fix in §6.x of Phase 2:
   either (a) raise uMenu's existing vi session to `ViServiceType_Manager`
   at startup (Plutonium-side change; touches SDL2 init), or (b) tear
   down the SDL2 vi session, init Manager, redo SDL2 init against the
   Manager session.  Option (a) is the design assumption but unverified
   — Phase 2.1 in §4 is the experiment that confirms which one works.
2. **Capture latency on real hardware may be >>33 ms.** If the
   experiment shows 100+ ms, the windowed UX feels laggy and we either
   need to switch to a shared-memory primitive (more scope) or accept
   "v3.1 windowed NROs run at sub-30 fps."
3. **The applet's framebuffer may be invalidated mid-frame during
   capture.** vi:s might tear or return a partial frame. Mitigation:
   capture with vsync awareness.
4. **Atmosphère may have changed `vi:s` semantics across HOS versions.**
   We test against HOS 20.0.0 only; users on older firmware may see
   different behavior.
5. **Memory:** capture buffer + decoded texture + uMenu's existing GPU
   pool may push past the 8 MB GPU memory budget. BG-2 should flag the
   tightness.

## 10. v3.2+ absorption candidates (BG-6 surfaced)

Per the creator directive 2026-05-18 evening: "Same with tesla overlay
and all of that stuff and how mods load. This will possibly be absorbed
as well later."

BG-6's audit identified the cleanest absorption candidates — all follow
the **HBMenu absorption pattern**: Q OS surfaces the catalog / config /
inventory in its own UI; the underlying loader/runtime sysmodule
(nx-ovlloader, sys-clk, etc.) is unchanged.

### Tier 1 — pure UI absorption (no sysmodule changes)

1. **sys-clk config surface.**  sys-clk is already on the creator's
   Switch; it ships a `.ovl` overlay + a manager NRO + writes
   `/config/sys-clk/config.ini`.  Q OS Vault → Settings → Performance
   reads/writes that INI file.  Profile picker, current-clock display.
   Pure UI — zero sysmodule work.
2. **`/switch/.overlays/*.ovl` catalog in Vault.**  Same model as the
   HBMenu → Vault absorption for NROs.  Users see installed Tesla
   overlays as launchable tiles in a Vault "Overlays" section.
   `nx-ovlloader` continues to do the actual loading; uMenu just shows
   the catalog and dispatches via the existing overlay-launch IPC.
3. **Per-title LayeredFS mod inventory in Vault.**  Enumerate
   `/atmosphere/contents/<TID>/romfs/` and `.../exefs/` for each
   installed title; show "active mods" in the title detail view.  Pure
   filesystem enumeration, no LayeredFS code changes.

### Tier 2 — out of scope / NO absorption

- **libtesla / nx-ovlloader runtime** — these are working community
  projects with active maintainers.  Q OS uses Tesla's vi:m composition
  technique (§2.3); we do NOT claim the overlay surface itself.
- **MissionControl** (BT controllers) — different problem domain.
- **ldn_mitm** — different problem domain.
- **sys-tweak / sys-patch** — these are creator-installed tweak modules
  with their own opinionated state; Q OS shouldn't try to be a control
  surface for arbitrary HOS patches.

The Tier-1 items become candidates for a v3.2 absorption pass after v3.1
ships and HW-stabilizes.

## 11. Hekate / Atmosphère / HOS technique extraction (creator-corrected scope)

Per the creator's 2026-05-18 correction: the goal is not to modify
Hekate / Atmosphère / HOS for v3.1; it's to **study their adjacent
solutions and copy their techniques where applicable**.

### Techniques worth copying

- **Tesla's `vi:m` max-Z-order overlay layer** (BG-6) — adopted in §2.3
  for window chrome composition.  Already in production via dozens of
  Tesla overlays; no R&D needed.
- **Atmosphère mitm pattern** (BG-2) — not used for v3.1 (the vi sub-
  session blocks it for our specific need), but the mitm pattern itself
  is replicable for other Q OS features (e.g., if v3.x wants to mitm
  `ldr:ro` for custom NRO loading semantics, the pattern is well-
  documented in libstratosphere).
- **HOS home-menu ↔ applet handoff state preservation** — uMenu IS the
  home menu replacement and already does this (theme/folder state
  survives applet switches).  No new technique to import; just
  confirming v3.1's `LibAppletMode_BackgroundIndirect` change must not
  break the existing state-preservation behavior.

### Techniques NOT worth copying

- **Hekate Nyx full-screen tab + status-bar UI** — Q OS already uses
  this pattern (BG-3); the visual language is identical.  No new
  insight.
- **Atmosphère's loader-mitm exefs redirection** — Q OS already uses
  this (uSystem injection into the qlaunch slot).  No new insight.
