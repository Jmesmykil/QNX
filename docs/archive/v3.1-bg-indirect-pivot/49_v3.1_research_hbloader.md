> Research deliverable for v3.1 windowed-homebrew feasibility. Do NOT implement based on this alone — pair with the sphaira-side research and the Atmosphère-mitm research before sketching architecture.

## 1. hbloader's frame-buffer acquisition path

### Key finding: hbloader does NOT own a framebuffer

Neither upstream nx-hbloader (`source/main.c`) nor uLaunch's replacement (uLoader, `src/projects/uLoader/source/ul/loader/loader_Target.cpp`) call any display, vi, or framebuffer APIs at all. There is no `framebufferCreate`, no `nwindowGetDefault`, no `viOpenDisplay`, no `SDL_Init` in either codebase.

hbloader's entire job is NRO loading and code mapping. It:
1. Sets up a heap (`svcSetHeapSize`).
2. Reads the NRO file off SD into the heap base (`fopen` / `fread`).
3. Maps NRO segments into executable virtual memory via `svcMapProcessCodeMemory` + `svcSetProcessMemoryPermission`.
4. Builds a `ConfigEntry[]` array (the HB ABI), which hands the NRO its heap, argv, process handle, applet type, etc.
5. Jumps directly into the NRO's entrypoint via `nroEntrypointTrampoline`.

**The display surface is never touched by hbloader.** It belongs entirely to the NRO itself.

The `nroEntrypointTrampoline` is the assembly stub in `loader_TargetImpl.s`. It does not return — the NRO takes over the thread.

### Upstream nx-hbloader (switchbrew) — same pattern

The upstream `loadNro()` in `source/main.c` (fetched from GitHub) follows the identical sequence:
- `svcSetHeapSize` → `svcMapProcessCodeMemory` → `svcSetProcessMemoryPermission` × 3 → build ConfigEntry[] → `nroEntrypointTrampoline`.
- No vi/nwindow/framebuffer calls anywhere.

**Conclusion for section 1:** hbloader acquires zero display resources. The entire display stack is the NRO's responsibility.

## 2. NRO vs hbloader ownership boundary

### Who owns the NWindow?

The NRO owns it — unconditionally. When an NRO calls `nwindowGetDefault()` (libnx), libnx calls `viInitialize` internally and acquires the vi:u or vi:s service handle for its own process. When it calls `framebufferCreate(fb, nwindowGetDefault(), ...)`, the FrameBuffer object wraps that NWindow.

hbloader passes ownership through the `ConfigEntry[]` HB ABI. Specifically:

- `EntryKind::AppletType` tells the NRO what applet slot it occupies (LibraryApplet or SystemApplication). This is the value libnx's `appletGetAppletType()` returns, which in turn governs which vi layer the NRO's `nwindowGetDefault()` opens.
- `EntryKind::OverrideHeap` gives the NRO its heap region. The NRO's libnx will call `svcSetHeapSize` with these bounds.
- `EntryKind::ProcessHandle` gives the NRO a handle to inspect its own process (used by some NROs for CodeMemory checks).

**The NRO's libnx calls `viOpenDisplay` + `viCreateLayer` + `nwindowCreate` using its own process's vi session.** hbloader never intercepts or pre-opens a vi layer. The NRO's vi session is distinct from uMenu's SDL2 surface.

### Could Q OS substitute its own NWindow before the NRO starts?

No, not through the existing HB ABI. The `ConfigEntry[]` has no entry type for passing a pre-opened NWindow or vi layer handle. The NRO initializes its own vi connection during `__nx_init` before `main()` runs — before any Q OS code could interact with it.

For windowed rendering to work, you would need to either:
- (a) Intercept the NRO's vi/nv calls through a mitm sysmodule running in the same process context, OR
- (b) Fork uLoader to suppress the NRO's `viOpenDisplay` and inject a shared-memory framebuffer instead — but this requires the NRO to cooperate or be patched at load time.

## 3. NRO-exit signaling

### How uSystem knows the NRO is done

There is no explicit "NRO exited" IPC message sent to uSystem. The signaling is entirely applet lifecycle:

1. uSystem launches uLoader as a library applet via `appletCreateLibraryApplet` → `appletHolderStart` (`la_LibraryApplet.cpp:41-64`).
2. uSystem's main loop polls `appletHolderCheckFinished(&g_LibraryAppletHolder)` through `la::IsActive()` (`la_LibraryApplet.cpp:68-76`).
3. When uLoader itself calls `exit(0)` (in `LoadTargetImpl` when `target_once && g_TargetTimes >= 1`), the applet process terminates, the holder's `StateChangedEvent` fires, and `appletHolderCheckFinished` returns true.

The state machine in `uSystem/source/main.cpp:1369-1408`:

```cpp
// main.cpp:1369
if(!la::IsActive() && g_LastLibraryAppletLaunchedNotMenu) {
    // uLoader just finished. Collect output if in choose-mode.
    if(g_ExpectsLoaderChooseOutput) {
        la::Pop(&target_opt_st);
        appletStorageRead(&target_opt_st, 0, &target_opt, sizeof(target_opt));
    }
    UL_RC_ASSERT(LaunchMenu(menu_start_mode));
    // If choose-mode, push ChosenHomebrew message to uMenu.
}
```

### uLoader's exit path

`loader_Target.cpp:405-418` (in `LoadTargetImpl`):
```cpp
if(g_TargetInput.target_once && (g_TargetTimes >= 1)) {
    auto target_opt = TargetOutput::Create(g_NextTargetPath, g_NextTargetArgv);
    UL_RC_ASSERT(smInitialize());
    UL_RC_ASSERT(WriteTargetOutput(target_opt));
    smExit();
    exit(0);   // <-- applet process ends here
}
```

`WriteTargetOutput` (in `loader_Input.cpp:55-73`) pushes a `TargetOutput` struct onto the applet output storage via `appletPushOutData`. uSystem reads this back with `la::Pop` only when `g_ExpectsLoaderChooseOutput` is true (choose-homebrew mode). In normal single-NRO launch mode (`target_once = false`), the NRO loops until it writes a new path to `g_NextTargetPath`, at which point uLoader re-invokes `LoadTarget()` to chain-load the next NRO.

**Summary:** uSystem detects NRO completion through `appletHolderCheckFinished` — a kernel event on the applet holder handle. There is no custom IPC. When the applet process exits, the kernel fires the event; uSystem polls it on a 10ms tick.

## 4. uSystem-side `smi::LaunchHomebrewLibraryApplet` implementation

### Client side (uMenu)

`src/projects/uMenu/include/ul/menu/smi/smi_Commands.hpp:58-71`:
```cpp
inline Result LaunchHomebrewLibraryApplet(const std::string &nro_path, const std::string &nro_argv) {
    const auto target_ipt = loader::TargetInput::Create(nro_path, nro_argv, false, "");
    return SendCommand(SystemMessage::LaunchHomebrewLibraryApplet,
        [&](ScopedStorageWriter &writer) {
            writer.Push(target_ipt);   // pushes ~3.5KB TargetInput struct
            return ResultSuccess;
        },
        [](ScopedStorageReader &reader) { return ResultSuccess; }
    );
}
```

The `SendCommand` helper (`smi_Protocol.hpp:222-253`) writes a `CommandCommonHeader{magic=0x21494D53, val=LaunchHomebrewLibraryApplet}` + the struct into a 0x8000-byte `AppletStorage`, pushes it through `appletHolderPushInData` to the running uLoader/uMenu library applet, then blocks waiting for the reply storage.

### Server side (uSystem)

Full flow in `uSystem/source/main.cpp`:

1. **SMI receive** (`main.cpp:836-847`): uSystem's `smi::ReceiveCommand` pops the storage from `la::Pop` (which wraps `appletHolderPopOutData` against `g_LibraryAppletHolder`). It reads the header, dispatches on `SystemMessage::LaunchHomebrewLibraryApplet`, pops the `TargetInput` struct, pushes an `Action{type=LaunchHomebrewLibraryApplet, target_input, choose_mode=false}` onto `g_ActionQueue`.

2. **Action dispatch** (`main.cpp:1149-1186`): on the next main-loop tick where `!la::IsActive()` (i.e., uMenu has terminated):
   ```cpp
   // main.cpp:1157-1184
   UL_ASSERT_TRUE(g_Config.GetEntry(HomebrewAppletTakeoverProgramId, hb_applet_takeover_program_id));
   // Release previous ECS slot (AMS-1.11 clean-exit fix):
   if(g_PendingEcsProgramId != 0) {
       ecs::UnregisterExternalContent(g_PendingEcsProgramId);
   }
   ecs::RegisterLaunchAsApplet(
       hb_applet_takeover_program_id,
       0,                                    // la_version
       "/ulaunch/bin/uLoader/applet",        // exefs path on SD
       &action.launch_loader.target_input,   // TargetInput payload
       sizeof(action.launch_loader.target_input)
   );
   g_LastLibraryAppletLaunchedNotMenu = true;
   ```

3. **`RegisterLaunchAsApplet`** (`ecs_ExternalContent.hpp:18-22`):
   ```cpp
   RegisterExternalContent(program_id, exefs_path);  // AMS ldr:shell cmd 65000
   la::Start(GetAppletIdForProgramId(program_id), la_version, args, args_size);
   ```

4. **`RegisterExternalContent`** (`ecs_ExternalContent.cpp:34-49`): calls `ldrShellAtmosphereRegisterExternalCode` (IPC cmd 65000 on `ldr:shell`), which tells Atmosphère's loader to substitute the applet's exefs with the SD path `/ulaunch/bin/uLoader/applet` for the next launch of that program ID.

5. **`la::Start`** (`la_LibraryApplet.cpp:118-133`): calls `appletCreateLibraryApplet(AppletId_Album, LibAppletMode_AllForeground)` → `libappletArgsPush` → `appletHolderPushInData(TargetInput)` → `appletHolderStart`. The Album applet slot is taken over by Atmosphère and uLoader runs instead.

**Critical timing note:** The action is deferred onto `g_ActionQueue` and processed only when `!la::IsActive()`. Since uMenu IS the active library applet at the time the command arrives, uSystem must wait for uMenu to terminate before it can launch uLoader. This is why uMenu calls `FadeOutToNonLibraryApplet() + Finalize()` — it kills itself to free the applet slot.

## 5. Smallest-possible-change sketch

### Honest assessment

This is a **large, multi-component change** — not 100 lines. Rough order of magnitude: **1,000–3,000 lines** of new/modified code spread across at least three components, plus open feasibility questions that require Atmosphère-mitm research to resolve.

### What would have to change

**The core problem:** The NRO calls `nwindowGetDefault()` and gets a vi layer backed by the display's scanout. Q OS has no way to intercept that call from outside the NRO's process — they run in the same process address space (uLoader maps the NRO directly into itself via `svcMapProcessCodeMemory`), but the vi service call goes out via IPC to the vi sysmodule.

**Option A: vi-mitm sysmodule (most correct, hardest)**

Atmosphère supports `mitm` sysmodules that intercept IPC sessions. A vi-mitm could intercept `viOpenDisplay` / `viCreateLayer` from the hbloader process and redirect the NRO's scanout layer to an offscreen buffer. uMenu (via a separate vi session) could then sample that buffer each frame and composite it as a texture.

- Function to intercept: `viCreateManagedLayer` (vi:m) or `viCreateLayer` (vi:u/s) — specifically the `CreateStrayLayer` or `CreateLayer` command on `IApplicationDisplayService`.
- The mitm would need to substitute a `SharedMemory`-backed surface in place of the real scanout layer.
- Q OS would read that shared memory from uMenu's SDL2 render loop and composite it.

**Feasibility block:** Cross-process shared framebuffer via vi is not a documented libnx primitive. `nwindow*` APIs (`nwindowCreate`, `framebufferCreate`) ultimately call `nv` (NVIDIA) IOCTLs to map GPU memory. Intercepting at the vi layer level is possible (vi is pure IPC); intercepting at the `nv` level (nvgfx, `nv-mitm`) is Atmosphère territory and more complex.

**Option B: fork uLoader, suppress NRO's vi init, inject shared mem**

Modify uLoader to not call `nroEntrypointTrampoline` directly, but instead:
1. Before jumping, patch the NRO's `viInitialize` / `nwindowGetDefault` function pointers in its GOT/PLT to redirect to stubs.
2. The stubs allocate a `SharedMemory` region and create a synthetic `NWindow` backed by it.
3. uMenu maps the same shared memory and samples it each frame.

Problem: libnx's `viInitialize` and `nwindowGetDefault` are in the NRO's own `.text`/`.rodata` (the NRO links statically against libnx). There is no PLT for libnx calls inside the NRO — they are direct calls or inlined. Patching would require disassembling the NRO at load time to find the vi call sites, which is fragile and NRO-specific.

**Option C: framebuffer capture via `nv-mitm` / nvgfx**

The NVIDIA GPU driver (`/dev/nvhost-*`, `nv:drv`, `nvgfx` sysmodule) is what actually flips scanout buffers. Atmosphère's `nv-mitm` can intercept `NVMAP_IOC_ALLOC` and `NVMAP_IOC_FROM_FD` to get handles to the NRO's GPU buffer allocations, then map them into uMenu's address space for sampling.

This is theoretically the cleanest approach (no NRO patching) but requires deep knowledge of the nvhost/nvmap IPC surface. The synthesis agent should check if Atmosphère's existing `nv-mitm` (if present in this fork's Atmosphere-libs) already exposes hooks.

**Option D: screenshot-based (pragmatic hack)**

The vi service supports `IApplicationDisplayService::CaptureScreenshot` (vi:s privilege only). uMenu runs as qlaunch (overlay applet), which means it has access to vi:s. It could call `CaptureScreenshot` on a 16ms interval and render the result as a texture in a Q OS window.

Latency: ~16–33ms per frame capture at best, plus compositor overhead. Not suitable for fast-moving NROs (RetroArch at 60fps would stutter severely). Could work for slow UI NROs like JKSV or hb-appstore.

Cost: ~50–100 lines if the vi:s screenshot API is already wired. Main risk: CaptureScreenshot may not be callable while a library applet is active (Nintendo's security model restricts vi:s callers). Needs verification.

### Summary

| Option | LOC estimate | Latency | NRO compat | Risk |
|--------|-------------|---------|------------|------|
| A: vi-mitm sysmodule | 1,500–3,000 | ~frame (16ms) | Universal | High — requires new sysmodule |
| B: uLoader GOT patch | 500–1,000 | ~frame | Fragile, per-NRO | High — static linking breaks it |
| C: nv-mitm capture | 1,000–2,000 | ~frame | Universal | High — nvhost IPC complexity |
| D: CaptureScreenshot | 50–100 | 33–66ms | Universal | Medium — vi:s permission gate |

Option D is the only one achievable in a single sprint. Options A/C are the correct long-term approaches but require the Atmosphère-mitm research brief to determine feasibility.

## 6. Open questions / unknowns

1. **vi:s CaptureScreenshot availability during library applet**: Can uMenu (running as qlaunch overlay) call `IApplicationDisplayService::CaptureScreenshot` while a library applet occupies the foreground? Nintendo's applet model may block this. Couldn't determine from source alone — requires a live test or Atmosphère source review.

2. **Does this fork include any nv-mitm or vi-mitm Atmosphere component?** The `src/libs/Atmosphere-libs/` tree contains `libstratosphere`, `libmesosphere`, `libvapours`, `libexosphere` — no sysmodule source. Whether the deployed Atmosphere on the target Switch has nv-mitm active is unknown.

3. **SharedMemory across applet process boundary**: On Switch, can two processes in the same applet session share memory via `svcCreateSharedMemory` / `svcMapSharedMemory`? The applet isolation model may restrict this. uLoader runs in the Album applet's process; uMenu would need to be running simultaneously (it isn't — it terminates before uLoader launches). This is the fundamental architectural conflict with the current launch sequence.

4. **uMenu termination is mandatory in the current design**: `la::IsActive()` blocks the action queue until uMenu is gone (`main.cpp:1150`). For windowed mode, uMenu must remain alive while the NRO runs. This requires either changing to `LibAppletMode_Background` (subapplet) instead of `LibAppletMode_AllForeground`, or running uLoader as a separate non-applet process. Neither is a small change.

5. **NRO cooperative mode**: Some NROs (notably sphaira) already support alternate rendering modes. The sphaira-side research brief should clarify whether sphaira can be told to render to an offscreen buffer via argv/env rather than requiring hbloader-level interception.

6. **`EntryType_AppletType` in ConfigEntry**: upstream hbloader hardcodes `AppletType_LibraryApplet` for applet-mode launches. If we were to pass a different applet type (e.g., a hypothetical "sublayer applet"), the NRO's vi init behavior might change. No evidence in libnx source that such a type exists — couldn't locate.
