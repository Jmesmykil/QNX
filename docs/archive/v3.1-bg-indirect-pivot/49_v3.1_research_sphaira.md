# v3.1 Research — Sphaira's Embedability

> **Authored:** 2026-05-18  
> **Scope:** Feasibility assessment for sphaira as the first "windowed homebrew" target  
> **Source material:** sphaira master branch (last push 2025-11-30, tag 1.0.0),  
> https://github.com/ITotalJustice/sphaira — all claims below cite specific files

---

## 1. Does sphaira have a "windowed mode"?

**No. There is no windowed mode in sphaira today, and no evidence one is planned.**

Evidence:

- **README.md** (https://github.com/ITotalJustice/sphaira/blob/master/README.md): The README
  lists file association, FTP, MTP, theme support, USB install, and App Store features. There
  is no mention of windowed mode, compositor hooks, hosted NRO mode, OOP mode, or any
  embedding API. Full text was fetched and searched; the words "windowed", "compositor",
  "embed", "hosted", and "OOP" do not appear.

- **Release notes** (tags 0.13.0 through 1.0.0, fetched via GitHub API): The five most recent
  release bodies contain no reference to windowed mode, host/guest NRO protocol, or Q OS
  integration. Tag 1.0.0 release body: "General system stability improvements to enhance the
  user's experience." No feature release in the fetched history mentions windowed mode.

- **Source code search** — searched `sphaira/source/app.cpp` (108,417 bytes) for the strings
  `windowed`, `compositor`, `embed`, `host`, `OOP`, `viCreate`, `viOpenDefaultDisplay`,
  `nwindowSetDimensions`, `SMI`, `smi::`: zero matches. The only `nwindow` hit is
  `nwindowGetDefault()` in `createFramebufferResources()` (line 2877), which is standard
  full-screen setup.

- **Open issues search** on the sphaira repo: no open issues with any of the above keywords.

**Conclusion:** The Q OS v3.0 README's claim that sphaira has "documented windowed mode hooks"
was speculative. There are no such hooks. Sphaira is a conventional full-screen NRO.

## 2. Sphaira's framebuffer + input initialization

### 2.1 Entry point

Source: https://github.com/ITotalJustice/sphaira/blob/master/sphaira/source/main.cpp

```
main(argc, argv)
  → construct App(argv[0])
  → Push MainMenu
  → Loop()
```

The entire framebuffer and input setup lives in `App::App()` constructor and
`App::Loop()`, defined in `sphaira/source/app.cpp`.

### 2.2 Framebuffer initialization sequence (App constructor)

Source: https://github.com/ITotalJustice/sphaira/blob/master/sphaira/source/app.cpp, ~line 1829

1. **`GetFrameBufferSize()`** — reads `appletGetOperationMode()`. Handheld → 1280×720.
   Console (docked) → 1920×1080. No argument to override.

2. **`dk::DeviceMaker{}.setCbDebug(deko3d_error_cb).create()`** — creates the deko3d device.
   No flags that would expose an external surface or external memory handle.

3. **`dk::QueueMaker{device}.setFlags(DkQueueFlags_Graphics).create()`** — graphics queue.

4. **`CMemPool` construction** — 16 MB image pool, 128 KB code pool, 1 MB data pool.
   All sizes are hardcoded; no external injected memory.

5. **`createFramebufferResources()`** — the critical line:
   ```cpp
   this->swapchain = dk::SwapchainMaker{device, nwindowGetDefault(), fb_array}.create();
   ```
   `nwindowGetDefault()` returns the libnx-managed NWindow for the current process.
   This is the system-assigned full-screen surface. There is no parameter that accepts
   an alternate NWindow or an externally provided surface handle.

6. **`nvgCreateDk(...)`** — NanoVG over deko3d, renders into the swapchain above.

### 2.3 Input initialization sequence (App constructor, ~line 1785)

Source: same file

```cpp
hidInitializeTouchScreen();
hidInitializeGesture();
hidInitializeKeyboard();
hidInitializeMouse();
padConfigureInput(8, HidNpadStyleSet_NpadStandard);
// padInitializeDefault(&m_pad);  // commented out by the author
padInitializeAny(&m_pad);
```

Key point: `padInitializeAny` is called directly in the constructor. There is no
init-time hook that would let a host process substitute a pre-configured pad handle
or intercept button state before sphaira reads it.

### 2.4 Main loop (App::Loop, ~line 473)

```cpp
while (!m_quit && appletMainLoop()) {
    // resize detection on applet mode change
    this->Poll();   // reads pad + touch + keyboard
    this->Update(); // dispatches to top Widget
    this->Draw();   // acquires swapchain slot, renders, presents
}
```

`Poll()` calls `padUpdate(&m_pad)` unconditionally (when not in touch mode).
`Draw()` calls `this->queue.acquireImage(this->swapchain)` and
`this->queue.presentImage(this->swapchain, slot)`. Both are direct calls to
the deko3d swapchain bound to `nwindowGetDefault()`. No abstraction layer sits
between `Poll` and the hardware input, and none sits between `Draw` and the
display output.

## 3. Embed-friendliness assessment

**Sphaira is not a good first target. Q OS's earlier README overstated the situation.**

Specific blockers:

### 3.1 Framebuffer: hardwired to nwindowGetDefault()

`nwindowGetDefault()` is a libnx global that returns the single NWindow bound to
the current process's display layer. To redirect sphaira's rendering into a Q OS
window rectangle, you would need to either:

- Replace `nwindowGetDefault()` with a custom NWindow backed by a shared-memory
  surface that Q OS composites — requiring libnx modifications or LD_PRELOAD-style
  symbol interposition (not available in the Switch homebrew toolchain), or
- Patch sphaira's `createFramebufferResources()` to accept an external NWindow
  parameter — a source-level fork, not a hook.

Neither path is non-invasive. The deko3d swapchain is constructed once at startup
and never replaced. There is no "set target surface" API.

The L-CYCLE-WINDOW-MANAGER-DESIGN.md (docs/L-CYCLE-WINDOW-MANAGER-DESIGN.md,
section 3.1) already documents why cross-applet framebuffer capture is not
feasible at the OS level (nvnss layers, applet memory isolation). The sphaira
source confirms the NRO side of that constraint: sphaira makes no attempt to
expose an alternative output surface.

### 3.2 Input: direct PAD ownership

`padInitializeAny` inside the constructor means sphaira owns the pad state from
the moment it is constructed. A host process cannot inject button events into
`m_pad` without patching the call site or implementing a custom `PadState`
wrapper. There is no virtual dispatch or callback hook on `Poll()`.

### 3.3 Init chain: services grabbed unconditionally

`userAppInit()` (called by libnx before `main()`) runs `appletLockExit()`,
`socketInitialize()`, `plInitialize()`, `nifmInitialize()`, `accountInitialize()`,
`setInitialize()`, `hidsysInitialize()`, `ncmInitialize()`. These all succeed only
in the correct applet context. Running sphaira "in-process" inside uMenu would
double-initialize several services and crash on the `appletLockExit()` assert
(uMenu already holds the exit lock).

### 3.4 Summary verdict

| Dimension | Status |
|---|---|
| Output surface redirectable without source changes | No |
| Input injectable without source changes | No |
| Service init safe in-process | No |
| IPC/SMI embedding API exists | No |
| Windowed mode planned upstream | No evidence |

Sphaira is a well-built, actively maintained NRO. It is an excellent full-screen
NRO target for the existing `smi::LaunchHomebrewLibraryApplet` path. It is not
a viable windowed compositing target without forking sphaira and implementing a
custom surface abstraction layer — a multi-month project on top of the OS-level
constraints that already block windowed NRO compositing entirely.

## 4. Input intercept point

**If Q OS ever implements windowed NRO compositing (requires OS-level work first),
the intercept point inside sphaira would be:**

`App::Poll()`, specifically the `padUpdate(&m_pad)` call at ~line 1139 in `app.cpp`.
This is the single place where physical button state is pulled into sphaira's
internal `Controller` struct that all widgets read.

A hypothetical patch would replace `padUpdate(&m_pad)` with a host-injected call:
```cpp
// Hypothetical only — not implementable without source fork
if (g_windowed_mode_host) {
    // receive translated button state from Q OS window manager
    g_windowed_mode_host->GetInjectedPadState(&m_pad);
} else {
    padUpdate(&m_pad);
}
```

Window-coordinate translation would map Q OS window-relative touch coordinates
to sphaira's `m_touch_info` struct, which is populated by
`hidGetTouchScreenStates(&state, 1)` earlier in `Poll()`.

Touch intercept point: `App::Poll()`, ~line 1048–1060 (the `hidGetTouchScreenStates`
block). A host would substitute window-local coordinates before the hit-test cascade
in `App::Update()` dispatches to widgets.

**Practical note:** both intercept points require source-level changes to sphaira.
There is no dynamic hook point that a host process could use without modifying
sphaira's code.

## 5. Alternative first-target NROs (two suggestions)

### 5.1 nx-hbmenu (https://github.com/switchbrew/nx-hbmenu)

**Why simpler:** nx-hbmenu is the reference homebrew menu maintained by switchbrew,
the same organization that maintains libnx. Its source was fetched as part of this
research.

Framebuffer: `graphicsInit()` in `nx_main/nx_graphics.c` uses the same
`dkSwapchainMakerDefaults(..., nwindowGetDefault(), ...)` pattern as sphaira.
Identical constraint at the OS level. However, the graphics module is a
**single C file** (nx_graphics.c + nx_graphics.h), not a 108 KB C++ class
hierarchy. Replacing `nwindowGetDefault()` with an injected NWindow is a
three-line change in one file, not a refactor across 30 files.

Input: `padInitializeAny(&g_pad)` in `main.c`, also a single file. Global
variable, no constructor side effects. Easier to patch.

Services: `nx_main/main.c` shows a minimal init sequence (pad, touch, theme
color, text rendering). Much smaller service surface than sphaira. Lower risk
of double-init conflicts.

Complexity: ~2,000 lines across a handful of C files. Sphaira is ~20,000 lines
of modern C++ with multiple subsystems (installer, FTP, MTP, App Store, dumper,
haze MTP, audio). For a proof-of-concept embedded surface, nx-hbmenu's
simplicity is a significant advantage.

**Caveat:** nx-hbmenu is C + deko3d. If Q OS's window compositor is SDL-based
(Plutonium), there is a renderer mismatch. Both deko3d and SDL ultimately write
to NWindow; they do not share a render context. The surface abstraction problem
exists here too. But the proof-of-concept patch surface is far smaller.

Upstream: https://github.com/switchbrew/nx-hbmenu  
Last updated: actively maintained (switchbrew org)

### 5.2 NXThemesInstaller (part of SwitchThemeInjector, https://github.com/exelix11/SwitchThemeInjector)

**Why simpler:** The NX-side installer (`SwitchThemesNX`) is a narrow-purpose NRO —
it reads theme files and patches SZS archives. It has no network stack, no FTP, no
MTP, no audio, no App Store. It is a UI wrapper around a file conversion library.

Framebuffer model: uses libnx's `framebufferCreate` / `framebufferMakeLinear` API
(classic linear framebuffer, not deko3d). This is the *simplest* possible Switch
rendering path. A linear framebuffer is a plain memory buffer; redirecting its
output to a Q OS texture would require copying one `u32[]` array per frame, which
is trivially implementable with a `memcpy` wrapper around `framebufferFlush`.

Input: standard `padUpdate` call in main loop. Single file structure.

The tradeoff: SwitchThemesNX is a utility tool with limited general appeal for
"windowed homebrew" demos. It would prove the surface-redirect mechanism but the
user value is narrow (most users run it once after install).

**Why it is still a better first target than sphaira:** the linear framebuffer
model has a well-defined redirect point (one `memcpy` per frame) that is much
easier to prototype than replacing a deko3d swapchain. A successful proof of concept
on SwitchThemesNX would validate the surface-redirect architecture before applying
it to more complex NROs.

Upstream: https://github.com/exelix11/SwitchThemeInjector  
Last active push: 2026-05-17 (very active)

## 6. Open questions / unknowns

1. **OS-level feasibility is the real gating question.** Both alternatives above still
   hit the same OS constraint documented in `docs/L-CYCLE-WINDOW-MANAGER-DESIGN.md`
   section 3.1: there is no mechanism for uMenu to capture another applet's framebuffer.
   The "inject NWindow" approach only works if the target NRO runs *in the same process*
   as uMenu, which collides with the double-service-init problem. The research here
   confirms the NRO side of that constraint; it does not resolve the OS side.

2. **sphaira's `hbl/` embedded loader.** Sphaira ships its own fork of nx-hbloader
   (`hbl/source/main.c`). This is how sphaira launches NROs from within itself —
   it acts as a mini-hbmenu. This does not create an embedding API; it is the same
   `nroEntrypointTrampoline` + `svcMapProcessCodeMemory` mechanism as stock hbloader.
   Q OS's uLoader already handles this path.

3. **deko3d NWindow abstraction gap.** deko3d's `DkSwapchain` takes a `NWindow*` at
   construction and cannot be retargeted. Any windowed-embed approach on deko3d NROs
   would require either: (a) a custom libnx/deko3d build that accepts an injected
   surface, or (b) a pixel-readback from the NRO's completed frame via GPU blit —
   not a path deko3d exposes without fork.

4. **Linear framebuffer NROs as the practical prototype path.** The oldest Switch NROs
   (pre-2021 era) use `framebufferCreate` / linear RGBA buffers. A linear buffer is
   directly readable. The render-redirect for those NROs is a memcpy, not a GPU
   swapchain intercept. If v3.1 windowed homebrew ships at all in the near term, the
   viable scope is "linear framebuffer NROs only" — not deko3d/SDL NROs like sphaira.

5. **Sphaira as a v3.1 launch partner is premature.** The Q OS README naming sphaira
   as the "planned first windowed-NRO target" set a false expectation. A more accurate
   framing: sphaira is the target for the *catalog* integration (it uses the same
   ForTheUsers CDN as hb-appstore; see `docs/SPHAIRA-CATALOG.md`). The windowed NRO
   feature, if it ships in v3.1, should target a linear-framebuffer utility NRO first.
   Sphaira belongs in v3.2+ after the OS-level surface routing is proven.
