# v3.1 Research — Atmosphère mitm + nv-gfx Capture Feasibility

**Date:** 2026-05-18  
**Author:** Research agent  
**Scope:** Can Atmosphère mitm be used to intercept the display path and composite NRO framebuffers inside a Q OS window?

---

## 1. Atmosphère mitm primitives

### Source locations (local tree)

- `src/libs/Atmosphere-libs/libstratosphere/include/stratosphere/sm/sm_mitm_api.hpp`
- `src/libs/Atmosphere-libs/libstratosphere/include/stratosphere/sf/hipc/sf_hipc_server_manager.hpp`
- `src/libs/Atmosphere-libs/libstratosphere/source/sf/hipc/sf_hipc_mitm_query_api.cpp`
- `src/libs/Atmosphere-libs/libstratosphere/source/sm/sm_mitm_api.cpp`

### Public interface

A sysmodule registers a mitm via:

```cpp
// sm_mitm_api.hpp — only compiled when ATMOSPHERE_OS_HORIZON && AMS_SF_MITM_SUPPORTED
Result InstallMitm(os::NativeHandle *out_port, os::NativeHandle *out_query, ServiceName name);
Result UninstallMitm(ServiceName name);
Result DeclareFutureMitm(ServiceName name);   // declare before service exists
Result AcknowledgeSession(Service *out_service, MitmProcessInfo *out_info, ServiceName name);
Result HasMitm(bool *out, ServiceName name);
```

`InstallMitm` goes to `smAtmosphereMitmInstall` in libnx, which calls into Atmosphère's patched sm.

### How it works

1. Sysmodule calls `sm::mitm::InstallMitm("vi:u", &port_handle, &query_handle)`.
2. Atmosphère's sm creates a shadow port. All subsequent `smGetService("vi:u")` calls are redirected to the sysmodule's port instead of the real vi server.
3. For each inbound session the sysmodule receives, sm also calls into the query service (`ShouldMitm`) — a callback registered via `RegisterMitmQueryHandle` — and the sysmodule answers with `true/false` per the connecting process's `MitmProcessInfo` (program ID, process ID).
4. If `ShouldMitm` returns true, the sysmodule gets the session AND a forward handle to the real service (via `AcknowledgeSession`), so it can proxy calls it doesn't want to handle via `ResultShouldForwardToSession()`.
5. If `ShouldMitm` returns false, sm hands the session directly to the real service — no overhead for excluded clients.

### ServerManager requirements

The sysmodule's `ServerManager` must be constructed with `CanManageMitmServers = true` in its `ManagerOptions`. The template enforces this at compile time.

### Constraints

| Constraint | Detail |
|---|---|
| **Must have service in SAC** | `InstallMitm` calls `ValidateAccessControl` — the sysmodule's NPDM must list the target service (e.g., `vi:u`) in its service-access list with "host" permission. |
| **One mitm per service** | Only one mitm can be active for a given service name at a time. |
| **Cannot mitm sub-sessions** | Mitm operates at the SM-registered named service level. A session obtained *from inside* another service (e.g., `IApplicationDisplayService` obtained from `vi:u` at cmd 0, or `IHOSBinderDriverRelay` at cmd 100) cannot be independently mitm'd — the mitm intercepts only the initial `smGetService("vi:u")` handshake, not sub-objects. |
| **AMS_SF_MITM_SUPPORTED gate** | The entire mitm infrastructure compiles out on non-Horizon targets (the `sf_mitm_config.hpp` `#if defined(ATMOSPHERE_OS_HORIZON)` guard). |
| **IsMitmDisallowed blocklist** | These program IDs cannot *use* mitm: Loader, Pm, Spl, Boot, Ncm, ams_mitm itself, Creport. The display path is NOT on this list. |

## 2. Display-path services + ownership

### The service graph for NRO framebuffer presentation

From reading libnx source (`framebuffer.c`, `native_window.c`, `vi.c`):

```
NRO calls framebufferCreate()
  → nvInitialize()          // opens "nv:u" or "nv:a" (nvdrv service)
  → nvMapInit()             // /dev/nvmap via nvdrv ioctl
  → nvFenceInit()           // /dev/nvhost-ctrl via nvdrv ioctl
  → viInitialize()          // opens "vi:u" (or vi:s, vi:m in priority order)
      → cmd 0 → IApplicationDisplayService (sub-session, NOT a named service)
      → cmd 100 → IHOSBinderDriverRelay     (sub-session, NOT a named service)
  → viCreateLayer() / viSetLayerScalingMode()
  → nwindowCreateFromLayer()
      → binderCreate() + binderInitSession() using IHOSBinderDriverRelay
      → bqConnect()
  → nwindowConfigureBuffer() via NvGraphicBuffer / nvmap handle
  → framebufferBegin() / framebufferEnd()
      → bqDequeueBuffer() + bqQueueBuffer() on the binder queue
```

### Per-service analysis

| Service | Host sysmodule | What it controls | Already mitm'd by AMS? | Mitm-able? |
|---|---|---|---|---|
| `vi:u` | `nvnflinger` / `vi` (Nintendo) | Allocates `IApplicationDisplayService` sessions; grants access to the compositor. Entry point for NRO layer creation. | No | Yes in theory — see constraints below |
| `vi:s` | same | Superset of `vi:u`; adds `ISystemDisplayService` | No | Same |
| `vi:m` | same | Full manager access including `IManagerDisplayService` | No | Same |
| `IHOSBinderDriverRelay` | sub-session from `vi:u` cmd 100 | The Android-style Binder IPC bus — hosts the buffer queue (dequeue/queue buffer) and the `NvGraphicBuffer` producer. This is where frames actually flow. | N/A — not SM-registered | **Cannot be mitm'd** via SM |
| `nv:u` / `nv:a` / `nv:s` / `nv:t` | `nvservices` (nns::nvdrv) | GPU hardware access via `/dev/nvmap`, `/dev/nvhost-*` ioctl interface. Allocates and maps framebuffer memory via `NVMAP_IOC_CREATE/ALLOC`. | No | Yes in theory — same constraints |
| `IApplicationDisplayService` | sub-session from `vi:u` | Layer creation, display management. | N/A — not SM-registered | **Cannot be mitm'd** |
| `nvnflinger` (internal) | `nvnflinger` | Compositor — reads from BQ and presents to display hardware. Not an SM service. | N/A | **Cannot be mitm'd** |
| `appletOE` / `appletAE` | `am` | Applet lifecycle, `IWindowController`, `GetIndirectLayerProducerHandle`. Mediates layer visibility. | No | Yes, but irrelevant to framebuffer content |

### Key structural finding

The actual pixel data flows through `IHOSBinderDriverRelay` (a sub-session) and the buffer queue binder objects — none of which are SM-registered named services. **Atmosphère mitm can only intercept at the named-service level.** By the time the NRO calls `bqQueueBuffer()`, it is communicating directly over the `IHOSBinderDriverRelay` session handle it received at startup — a handle that was obtained before any mitm interception could occur at the layer level.

Mitm-ing `vi:u` would let you intercept layer creation (so you could see which NROs opened a display layer and control what parameters they used), but it would NOT give you access to the frame data itself.

## 3. Prior display-mitm attempts (community + Atmosphère history)

### Atmosphère issue tracker search

A search of Atmosphère's GitHub issues (`display mitm`, `vi mitm`, `screen capture`, `nv mitm`, `compositor`, `framebuffer`) found **no issues, PRs, or discussions related to display path interception**. The closest hits:

- Issue #232 (2018-10-18): "Display Atmosphère next to firmware version" — a text overlay request, not framebuffer capture.
- Issue #1924 (2022-07-25): "allow displaying HTML content in applications" — web applet injection, not graphics interception.

No display mitm PR or design doc exists in the Atmosphère repository as of 2026-05-18.

### Community projects

No known community sysmodule that mitm's `vi:u`, `nv:u`, or `IHOSBinderDriverRelay` for the purpose of framebuffer capture or windowed composition could be found. Screen-capture projects on Switch (e.g., `sys-ftpd`, `nxdumptool`, screenshot via `caps:sc`) work at the capture service level — they read a saved framebuffer snapshot, not a live compositor stream.

The `caps:sc` (screenshot control) and `caps:ss` services documented on switchbrew do expose a saved display framebuffer image, but this is a still-capture mechanism at a point in time, not a live stream that would enable compositing.

### Conclusion on prior work

No one has successfully mitm'd the display path for live framebuffer interception on Switch. The structural reason (sub-session invisibility to SM mitm) explains why: it is not a matter of no one having tried — it is architecturally blocked.

## 4. Three architectural options

### Option A: Fork nx-hbloader

**Concept:** nx-hbloader (upstream) and uLoader (our fork) create the `NWindow` that the NRO inherits. If we own that NWindow creation, we control the buffer queue and can redirect frames to a texture we also own.

Specifically: instead of calling `nwindowCreateFromLayer()` with a real vi layer, create a "synthetic" NWindow backed by a shared-memory buffer, then composite that buffer into the Q OS desktop using a second deko3d pass.

**What has to change:**

- uLoader must create the synthetic NWindow (replacing the vi layer with a shared-memory BQ). This is non-trivial: NWindow creation normally involves opening `vi:u` for a layer; a headless NWindow without a real vi layer would need either a dummy vi layer (invisible to the compositor) or a wholly synthetic binder session that the NRO's `bqQueueBuffer` calls reach.
- uMenu must composite that shared-memory buffer as a texture overlay each frame.
- uLoader must own a second vi layer or deko3d texture for the composited result.
- Per-HOS-version maintenance: the Homebrew ABI (`ConfigEntry.AppletType`, `OverrideHeap`, etc.) is versioned. Every HOS update that changes the hbloader ABI requires a corresponding uLoader update. We already own uLoader; this is the maintenance cost we already pay.

**NRO modification required:** None. NROs call `framebufferCreate(win, …)` with whatever NWindow they were handed in HBABI. If we hand them a synthetic NWindow, they render into it without modification.

**Feasibility:** 3/5  
The mechanism is clear — we already own uLoader and understand the HBABI — but it requires implementing a synthetic binder buffer queue that the NRO's libnx runtime can use unmodified. That BQ must accept `bqDequeueBuffer`/`bqQueueBuffer` IPC without a real vi layer behind it. One approach: create a minimal vi layer via `viCreateStrayLayer()` and redirect its buffer queue handle, then intercept frames via the nvmap handle cross-process sharing (`NVMAP_IOC_EXPORT_FOR_ARUID` / `NVMAP_IOC_IS_OWNED_BY_ARUID`). This is technically feasible but requires low-level BQ implementation work.

**Blast radius:** uLoader only. uMenu changes are additive (new rendering overlay). Does not touch Atmosphère, does not affect other NRO launches.

**Who does the work:** Q OS team (uLoader + uMenu). No Atmosphère contribution needed.

---

### Option B: Mitm a display service

**Concept:** Install a sysmodule that mitm's `vi:u`. Intercept layer creation calls from the NRO, create a synthetic layer, redirect frame submission to a buffer we composite ourselves.

**What the evidence says:**

- Mitm of `vi:u` is permitted by Atmosphère sm — `vi:u` is not on the `IsMitmDisallowed` blocklist and is not a protected program-ID caller.
- The sysmodule's NPDM would need `vi:u` (or `vi:s`) in its service-access list with host permission.
- **However:** Mitm intercepts `smGetService("vi:u")` — the initial session handshake. After that, the NRO holds a session to `IApplicationDisplayService` (a sub-session obtained from `vi:u`), and then to `IHOSBinderDriverRelay` (a sub-session from `IApplicationDisplayService`). Neither of these sub-sessions is SM-registered. Mitm does not see them.
- The actual frame data flows over `IHOSBinderDriverRelay` → `bqQueueBuffer`. This call is completely invisible to the vi:u mitm sysmodule.
- Conclusion: Mitm-ing `vi:u` would let you observe/block layer creation, but gives you **zero visibility into frame content**. You cannot intercept `bqQueueBuffer` this way.

**Alternative: mitm nv:u**  
`nv:u` (nvdrv) handles nvmap allocation and ioctl. Mitm-ing it would intercept `nvMapCreate` calls and potentially the `NVMAP_IOC_EXPORT_FOR_ARUID` mechanism. This is more promising for accessing the underlying memory, but:
- You intercept ioctls as raw byte buffers, not typed structs — every HOS update that changes nvdrv ioctl layout breaks the sysmodule.
- You still don't intercept the presentation timing (`bqQueueBuffer`) — you'd have to poll the nvmap memory directly.
- This does not exist in current Atmosphère and would require building a new mitm sysmodule from scratch with extensive nvdrv ioctl reverse engineering.

**Feasibility:** 1/5 for the framebuffer-capture goal  
The SM-level mitm mechanism simply cannot reach the sub-session where frame data flows. Mitm of `vi:u` alone gives no access to frame content. Mitm of `nv:u` would require massive RE work with high fragility.

**Blast radius:** High. A vi:u mitm sysmodule intercepts EVERY process that opens vi:u — system applets, games, the compositor itself if it uses vi:u. A bug causes a system-wide display failure. Recovery requires SD card intervention to remove the sysmodule.

**Who does the work:** Q OS team (new sysmodule) + extensive nvdrv RE. Atmosphère team not involved, but their infrastructure is used.

**NRO modification required:** None (if it worked). But it doesn't work for frame capture.

### Option C: Cooperative ABI ("hosted NRO" protocol)

**Concept:** Define a new optional entry in the Homebrew ABI (`ConfigEntry`). An NRO that opts in to the "hosted" protocol receives a `ConfigEntry` of type `HostedWindow` containing a deko3d-compatible shared texture handle or nvmap ID provided by uLoader/uMenu. The NRO renders into that shared texture instead of (or in addition to) creating its own vi layer. Q OS composes the result.

NROs that do not include this entry continue to launch full-screen as today.

**What the evidence says:**

- nvmap supports `NVMAP_IOC_EXPORT_FOR_ARUID` and `NVMAP_IOC_IS_OWNED_BY_ARUID` for cross-process buffer sharing between AppletResourceUser IDs. This is the documented mechanism for inter-process GPU buffer sharing on Switch.
- uMenu and uLoader run in the same applet context (uLoader is launched by uMenu via `smi::LaunchHomebrewLibraryApplet`), so they share an ARUID context. The NRO could use the exported nvmap handle to write into uMenu's texture memory.
- deko3d's `DkMemBlockMaker` does NOT expose a cross-process import API — there is no `externalHandle` field in `DkMemBlockMaker` as of the current header. deko3d manages memory internally per-process.
- However, the underlying nvmap ID mechanism bypasses deko3d. If uMenu allocates a texture via deko3d, it can separately obtain the nvmap ID of that memory (via `nvMapGetId`) and share it via the HBABI config entry. The hosted NRO can then map that nvmap ID into its own address space and write pixels there using raw libnx calls (not deko3d).
- This is the same mechanism that `framebufferCreate` already uses internally — `grbuf.nvmap_id = nvMapGetId(&fb->map)` — so it is proven to work for NROs.

**What has to change:**

- Define a new `ConfigEntry` kind (e.g., `EntryKind::HostedNvmapId = 14`) in uLoader's HBABI header.
- uMenu allocates a texture-sized nvmap buffer, exports it via ARUID, passes the nvmap ID in the new ConfigEntry.
- uLoader adds the entry to `target_cfg_entries[]` when launching in hosted mode.
- The NRO (opt-in) checks for the new config entry in its `__appInit`, maps the nvmap ID, and renders into it instead of creating a framebuffer.
- uMenu polls or event-signals each frame when the NRO has committed a new frame, composites the texture into the desktop view.
- A libnx helper library (or fork) could wrap this protocol for NRO developers.

**NRO modification required:** Yes, for NROs that want windowed mode. Existing NROs continue to work full-screen. This is an opt-in protocol, not a forced redirect.

**Feasibility:** 3.5/5  
The nvmap cross-process sharing mechanism is documented and used by the existing framebuffer path. The HBABI extension is straightforward (we already own the config-entry table in uLoader). The main unknown is synchronization: coordinating when the NRO has finished a frame and uMenu should composite. A simple shared-memory semaphore or the existing `NvFence` mechanism could handle this. The biggest risk is that the NRO must opt in, limiting initial usefulness to a curated set of homebrews.

**Blast radius:** Minimal. Only affects uLoader (new config entry, conditional allocation) and uMenu (new texture compositing pass). No sysmodule, no Atmosphère change. An NRO that does not check for the new entry behaves identically to today.

**Who does the work:** Q OS team (uLoader + uMenu + optional libnx helper). NRO developers who want windowed mode. No external dependency.

## 5. Deko3d shared-texture feasibility

### What deko3d exposes

From `deko3d.h` (devkitPro):

- `DkMemBlockMaker` has fields: `device`, `size`, `flags`, `storage`. **No external handle import field.**
- `DkResHandle` is an opaque 32-bit handle — process-local, not cross-process.
- `Fence::import(uint32_t id, uint32_t value)` — imports a fence (sync primitive), not a texture.
- There is no `DkMemBlock::exportHandle()` or `DkMemBlock::importExternal()` in the public API.

### What the underlying platform provides

Under deko3d, memory blocks are backed by nvmap objects. The nvmap IPC layer provides:

- `NVMAP_IOC_CREATE` + `NVMAP_IOC_ALLOC` — create and allocate a GPU-accessible memory object.
- `NVMAP_IOC_EXPORT_FOR_ARUID` — bind a nvmap object to another process's AppletResourceUserId.
- `NVMAP_IOC_IS_OWNED_BY_ARUID` — verify cross-process ownership.
- The nvmap ID (`nvMapGetId`) is a 32-bit value that can be passed via IPC/HBABI and re-opened in another process via `nvMapFromId`.

### Assessment

**deko3d itself has no cross-process sharing API.** However, the nvmap layer underneath it does. A hosted NRO would use raw libnx nvmap calls (not deko3d) to map the shared buffer, then write pixels using CPU writes or GPU commands issued via `nv:u` ioctls. uMenu would own the deko3d texture side and could use it as a render source.

This is workable but requires the hosted NRO to bypass deko3d and use raw nvmap + nvhost ioctls for writing — a lower-level interface that most NRO developers do not currently use. A thin wrapper library would be needed to make it accessible.

## 6. Honest recommendation

**Option C (cooperative ABI / hosted NRO protocol) is the only path supported by the evidence.**

Reasons:

1. **Option B is structurally blocked.** Atmosphère mitm operates at the SM named-service level. The display frame data flows through `IHOSBinderDriverRelay`, a sub-session that is never visible to SM mitm. No amount of engineering makes SM mitm capture frames — the kernel's IPC architecture prevents it.

2. **Option A is feasible but has a higher implementation floor.** It requires implementing a synthetic binder buffer queue in uLoader — essentially a partial reimplementation of the vi compositor protocol inside the homebrew loader. This is achievable (we own uLoader), but it is more work than Option C for the same result, and it requires the synthetic NWindow to faithfully emulate enough of the Binder/IGraphicBufferProducer interface that unmodified NROs don't crash.

3. **Option C reuses proven mechanisms.** The nvmap cross-process export (`NVMAP_IOC_EXPORT_FOR_ARUID`) is the exact same mechanism that `framebufferCreate` uses internally today. The HBABI config-entry extension is the same table we already manage in uLoader. No new kernel primitives, no new sysmodules, no Atmosphère dependency.

4. **The opt-in constraint is not a blocker — it is correct behavior.** A windowed homebrew feature that requires NRO cooperation gives NRO developers explicit control and avoids breaking the many homebrews that assume full-screen, full-GPU access.

**Recommended path:**

- Extend the HBABI with a new `EntryKind::HostedNvmapId` config entry.
- uMenu allocates a compositor texture + nvmap buffer, exports it via ARUID before launching the NRO.
- uLoader passes the nvmap ID in the new config entry.
- Define a thin `libqos-hosted-nro` header/library that NRO developers include to opt in.
- For v3.1 milestone: deliver the protocol + one reference NRO (e.g., a modified hbmenu or a test NRO) that renders windowed.
- Full-screen launch path is completely unchanged.

## 7. Open questions / unknowns

1. **ARUID sharing between uMenu and uLoader:** Confirm that uLoader (launched as a library applet via `smi::LaunchHomebrewLibraryApplet`) inherits the same ARUID as uMenu, making `NVMAP_IOC_EXPORT_FOR_ARUID` usable between them. If they have distinct ARUIDs, the sharing mechanism needs adjustment (e.g., use a `TransferMemory` sysvc instead).

2. **Frame synchronization:** Define the protocol for the NRO signaling "frame ready" to uMenu. Candidates: (a) a shared-memory atomic flag, (b) an `NvFence` passed in another HBABI entry, (c) a named IPC service from uMenu that the NRO calls. Option (c) adds a round-trip per frame; option (b) requires the NRO to submit a fence on queue — feasible since `framebufferCreate` already does this.

3. **Synthetic NWindow vs real vi layer:** Option A still needs a decision on whether the NRO gets a *real* vi layer (which the compositor shows, and we intercept by owning the nvmap backing) vs a *synthetic* one. The real-vi-layer approach has less protocol complexity but means the system compositor is still rendering the NRO full-screen somewhere — which may or may not conflict with Q OS compositing.

4. **deko3d texture format alignment:** The hosted buffer must use a deko3d-compatible block-linear format (matching `NvLayout_BlockLinear` + `NvKind_Generic_16BX2`). Confirm that uMenu's deko3d texture allocation can specify the same nvmap kind as the NRO's `NvGraphicBuffer` format.

5. **uLaunch upstream parity:** If windowed NRO support ships in Q OS, how much of the infrastructure can be contributed back to upstream uLaunch? The HBABI extension in particular should be designed to be upstream-compatible.

6. **Compositing overhead:** A hosted NRO renders to a shared buffer; uMenu must composite that buffer each frame at 60fps. Measure the deko3d blit overhead at 1080p (the Plutonium renderer already runs at 1920×1080) to confirm the compositor frame budget is not exceeded.
