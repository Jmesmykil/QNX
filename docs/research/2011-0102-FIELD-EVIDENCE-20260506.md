# 2011-0102 Field Evidence — uSystem on FW22 / AMS 1.11.1

2026-05-06.

## The error — exact mechanism

`2011-0102` = module 11 (HIPC), description 102 = `0xCC0B`. Defined in
`Atmosphere-libs/libvapours/include/vapours/results/hipc_results.hpp`:

```
R_DEFINE_NAMESPACE_RESULT_MODULE(ams::sf::hipc, 11);
    R_DEFINE_ABSTRACT_ERROR_RANGE(OutOfResource, 100, 299);
        R_DEFINE_ERROR_RESULT(OutOfSessionMemory, 102);
```

Returned from one site —
`libstratosphere/.../sf_hipc_server_session_manager.hpp`,
`ServerSessionManager::CreateSessionImpl`:

```
ServerSession *session_memory = this->AllocateSession();
R_UNLESS(session_memory != nullptr, sf::hipc::ResultOutOfSessionMemory());
```

`AllocateSession()` walks the static
`util::TypedStorage<ServerSession> m_session_storages[MaxSessions]` array
tracked by `bool m_session_allocated[MaxSessions]`. `MaxSessions =
ServerSessionCountMax (0x40) - MaxServers`. **It is a compile-time pool
capped at 64.** Failure means every slot is in use — not heap exhaustion,
not a kernel limit, not transient fragmentation. Deterministic per-binary
per-firmware: same template parameters → same pool → same failure point.
Distinct from `OutOfSessions` (131–139, kernel handles) and `OutOfDomains`
(200). The `R_ABORT_UNLESS` at uSystem+0x36440 means uSystem aborted on
the bubbled Result, almost certainly at a `RegisterServer` / IPC-bind site
right after the libnx `nsInitialize` stubs. The paired `am` `0x10801 /
0xC880` is consistent with am refusing because its peer (uSystem) failed
to register.

## uLaunch upstream FW20+ status

Releases (https://github.com/XorTroll/uLaunch/releases):
1.2.3 (2026-01-24) AMS 1.10.2 / FW 21.2.0; 1.2.2 (2025-12-22) AMS 1.10.1
/ 21.1.0; 1.2.1 AMS 1.9.1 / 20.1.0; 1.2.0 AMS 1.9.0 / 20.0.1.
**Upstream uLaunch has never shipped an AMS 1.11.x build.** AMS 1.11.0
introduced a documented breaking change: applications/applets must
perform a clean exit via the relevant IPC commands (Atmosphère
changelog). `unew` branch is active (309 commits) but no AMS 1.11 tag
exists. Q OS's fork inherits the gap.

## Transient vs deterministic

Pool exhaustion in a fixed array is deterministic per binary per firmware.
Reboot frees the pool (fresh process = fresh array), so a power-cycle
masks the symptom — the trigger condition recurs each time uSystem hits
the same init path. The intermittent boot success indicates a **race** in
session lifecycle ordering between uSystem and a peer sysmodule, not a
leak. Same root-cause class as the AMS 1.11 lifecycle break.

## Concrete remediation reported

No public CFW launcher has shipped a working AMS 1.11.x patch. Generic
remediation that surfaced for the FW21 break: **recompile against libnx
≥ 4.10.0**, audit every `*Initialize` / `*Exit` pair so applets return via
the new IPC contract. Server-side: raise `MaxSessions` via `ServerManager`
template parameter; ensure every opened session is closed on the failure
path (`ON_RESULT_FAILURE { this->DestroySession(...); }` covers
construction, app-level callers must close on error too).

## Verdict on "update AMS to fix this"

**Wrong direction per evidence.** AMS 1.11.x is the disruptor, not the
fix — it added the clean-exit IPC contract that broke homebrew at large.
Empirical floor is what upstream 1.2.3 was built against: **AMS 1.10.2 /
FW 21.2.0**. Real fix is (a) match that, or (b) port the fork forward —
recompile against libnx ≥ 4.10.0, adopt the AMS 1.11 clean-exit IPC
pattern, and audit `MaxSessions` plus session-close paths in uSystem.
**No field evidence supports "newer AMS resolves OutOfSessionMemory"**;
source shows it is a code-side pool/lifecycle bug, not an AMS bug.
